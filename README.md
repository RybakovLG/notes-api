# notes-api

REST API для заметок на Node.js и Express 5 — учебный проект: Node изнутри, слои приложения, конкурентный доступ к данным, тесты.

Данные хранятся в JSON-файле. Это осознанное упрощение: на нём видны проблемы, которые потом решает база данных (гонки, атомарность записи).

## Стек

Node.js 26 (TypeScript запускается напрямую, без сборки) · Express 5 · Zod · Vitest + Supertest · Biome · pnpm

## Запуск

```bash
pnpm install
cp .env.example .env
pnpm dev        # с перезапуском при изменениях
pnpm start
```

| Переменная | Назначение |
|---|---|
| `PORT` | Порт сервера, обязателен |
| `NOTES_PATH` | Путь к файлу с заметками (`.json`), относительно корня проекта |

При неверной конфигурации сервер не стартует и пишет, какая переменная не так.

## API

| Метод | Путь | Успех | Ошибки |
|---|---|---|---|
| GET | `/notes` | 200, массив заметок | |
| POST | `/notes` | 201, созданная заметка | 400 |
| GET | `/notes/:id` | 200, заметка | 400, 404 |
| PUT | `/notes/:id` | 200, изменённая заметка | 400, 404 |
| DELETE | `/notes/:id` | 204 | 400, 404 |

Неразрешённый метод на существующем пути → 405 с заголовком `Allow`.

Заметка: `{ "id": "<uuid>", "text": "..." }`. Тело запроса: `{ "text": "..." }`.

Ошибки в формате [problem+json (RFC 9457)](https://www.rfc-editor.org/rfc/rfc9457):

```json
{
  "type": "/problems/validation-error",
  "title": "Validation error",
  "status": 400,
  "detail": "Неверный формат данных",
  "instance": "/notes/abc",
  "code": "VALIDATION_ERROR",
  "errors": [{ "in": "params", "field": "id", "message": "..." }]
}
```

## Структура

```
src/
  server.ts        запуск, корректное завершение по SIGTERM/SIGINT
  app.ts           приложение Express (без listen — так его тестируют)
  config.ts        конфиг из окружения, проверка при старте
  routes/          маршруты и 405
  controllers/     HTTP-слой: запрос → вызов репозитория → ответ
  repositories/    работа с файлом, очередь записи
  middlewares/     валидация (Zod), обработчик ошибок
  models/          схемы и типы
tests/             интеграционные тесты через Supertest
```

## Решения

### Параллельные запросы теряли заметки — очередь записи

Так как для учёбы используется файл на диске в качестве БД, это накладывало часть ограничений на параллельную работу с ним. Очередь записи гарантирует поэтапную работу с файлом.
Например, два запроса читают один и тот же старый файл, и запись второго затирает первый. Без очереди 50 параллельных созданий заметки оставили в итоговом файле 3 заметки на одном из тестов. Ограничение: очередь защищает только в рамках одного процесса.

### Чтение ловило недописанный файл — атомарная запись через временный файл

Без атомарной записи получение файла в процессе записи могло приводить к ошибке. `rename` подменяет файл одним шагом, поэтому чтение видит либо старый файл, либо новый, недописанного не бывает.

### Код разделён на слои: роуты, контроллеры, репозиторий

В процессе написания кода увидел смешение ответственностей.
Изучил подходы к построению приложений - выбрал слоистую архитектуру:

- Роут — собирает мидлвары по путям.
- Контроллер — работает с http методами - принял, передал, дождался, выбросил ошибку, ответил.
- Репозиторий — работа с БД, очередь записи, запись/чтение в файл.

### Ошибки в едином формате problem+json

Ошибки должны быть одинаковы для клиента.
Выбирал формат ошибок, изучал стандарты, нашёл современный — RFC 9457.

- Поле `code` стабильно, фронт опирается на него, а не на текст;
- `errors` — массив, в каждом элементе `in` и `field`, чтобы подсветить нужное поле формы;
- При 500 стек наружу не уходит.

### Интеграционные тесты и тест на гонку

Было неясно, всё ли работает и проверяется как необходимо.
Тесты проверяют полный путь эндпоинтов, их валидаторов, ответы, гонку параллельных запросов.
У каждого тестового файла свой временный файл с заметками, поэтому тесты не трогают реальные данные.
